## What Blade Actually Is

- **Blade**: Laravel's templating engine — every Blade file is named `something.blade.php` and lives inside `resources/views/`.
- Under the hood, Blade files are **compiled into plain PHP and cached**, so using Blade's syntax has effectively zero performance cost compared to writing raw PHP yourself.
- A controller renders a Blade view like this (from note 03):

```php
return view('products.index', ['products' => $products]);
```

- `'products.index'` — Laravel converts the dot into a folder separator, so this loads `resources/views/products/index.blade.php`.
- The second argument is an associative array of data passed into the view — inside the Blade file, each array key becomes a variable (`$products` in this example).

> 💡 **Tip:** As a frontend dev, think of a Blade view roughly like a JSX component that receives "props" — except here, those props are passed in from the Controller via that array.

## Displaying Data

```blade
{{-- Auto-escaped output (safe, default) --}}
<p>{{ $product->name }}</p>

{{-- Raw, unescaped output (dangerous unless fully trusted) --}}
<p>{!! $product->description_html !!}</p>
```

- **`{{ }}`**: outputs a PHP expression, automatically running it through `htmlspecialchars()` first — this converts things like `<script>` into harmless text, protecting you from **XSS (Cross-Site Scripting)** attacks.
- **`{!! !!}`**: outputs a PHP expression **without** escaping — the raw HTML is rendered as-is.

> ⚠️ **Warning:** Only ever use `{!! !!}` with content you fully control or have already sanitized (e.g., HTML generated by a trusted rich-text editor library). Using it on raw user input is a serious security hole.

**Comments** (never rendered to the browser, unlike HTML comments):

```blade
{{-- This comment will not appear in the page source --}}
```

## Conditionals

```blade
@if($product->stock > 0)
    <span class="badge">In Stock</span>
@elseif($product->is_preorder)
    <span class="badge">Pre-order</span>
@else
    <span class="badge">Sold Out</span>
@endif
```

- Behaves exactly like PHP's `if/elseif/else`, just with Blade's `@` syntax and no need for `<?php ?>` tags.

**`@unless`** — the inverse of `@if`:

```blade
@unless($user->isAdmin())
    <p>You do not have admin access.</p>
@endunless
```

**`@isset` / `@empty`** — safely check if a variable exists or is empty:

```blade
@isset($product)
    {{ $product->name }}
@endisset

@empty($products)
    <p>No products found.</p>
@endempty
```

## Loops

```blade
@foreach($products as $product)
    <li>{{ $product->name }}</li>
@endforeach
```

**`@forelse`** — a loop with a built-in "what if the list is empty" fallback (very common in real apps):

```blade
@forelse($products as $product)
    <li>{{ $product->name }}</li>
@empty
    <p>No products yet.</p>
@endforelse
```

- `@forelse` saves you from writing a separate `@if(count($products) > 0)` check before every loop.

Other loop directives, identical to their plain PHP equivalents:

```blade
@for($i = 0; $i < 10; $i++)
    Item {{ $i }}
@endfor

@while($condition)
    ...
@endwhile
```

## The `$loop` Variable

Inside any `@foreach`, Blade automatically gives you a `$loop` object with useful metadata about the current iteration — no manual counters needed.

```blade
@foreach($products as $product)
    <p>{{ $loop->iteration }}. {{ $product->name }}</p>

    @if($loop->first)
        <p>(This is the first product)</p>
    @endif

    @if($loop->last)
        <hr>
    @endif
@endforeach
```

| Property | Meaning |
|---|---|
| `$loop->index` | Current iteration, zero-based (0, 1, 2...) |
| `$loop->iteration` | Current iteration, one-based (1, 2, 3...) |
| `$loop->first` | `true` on the first pass |
| `$loop->last` | `true` on the final pass |
| `$loop->count` | Total number of items in the loop |
| `$loop->remaining` | Items left after the current one |

> 💡 **Tip:** `$loop` even works inside **nested** loops — Blade gives you `$loop->parent` to reach the outer loop's data from within an inner one.

## Layouts: `@extends`, `@section`, `@yield`

Rather than repeating your `<html>`, `<head>`, navbar, and footer on every single page, Blade lets you define one master layout and have every page "fill in the blanks."

**The master layout** (`resources/views/layouts/app.blade.php`):

```blade
<!DOCTYPE html>
<html lang="en">
<head>
    <meta charset="utf-8">
    <title>@yield('title', 'My App')</title>
</head>
<body>
    @include('partials.navigation')

    <main>
        @yield('content')
    </main>

    @include('partials.footer')
</body>
</html>
```

**A page that uses that layout** (`resources/views/products/index.blade.php`):

```blade
@extends('layouts.app')

@section('title', 'All Products')

@section('content')
    <h1>Our Products</h1>
    @foreach($products as $product)
        <p>{{ $product->name }}</p>
    @endforeach
@endsection
```

- **`@extends('layouts.app')`**: tells Blade "this page is built on top of that layout file."
- **`@yield('content')`**: a placeholder in the layout — marks *where* child-page content should be inserted.
- **`@section('content') ... @endsection`**: in the child view, defines what content actually fills that named placeholder.
- **`@section('title', 'All Products')`**: a shorthand one-line version for simple values, instead of the block form.

> 💡 **Tip:** As a React dev, this is conceptually identical to a shared `<Layout>` wrapper component with a `{children}` slot — `@yield` is the Blade version of `{children}`.

> ⚠️ **Warning:** Every `@section` you open with the block syntax must be closed with `@endsection` (or `@show`, which is like `@endsection` but also immediately yields the content — used inside the layout itself when a section needs a default value).

## Includes (Partial Views)

```blade
@include('partials.navigation')

{{-- Passing extra data into the included view --}}
@include('products.partials.card', ['product' => $product])
```

- **`@include`**: pulls in another Blade file's content inline — useful for reusable chunks like navbars, footers, or repeated card markup that *don't* need the more powerful features of full Components (below).

| Feature | `@include` | Component (`<x-...>`) |
|---|---|---|
| Reusability | Good for simple static partials | Better for reusable, logic-driven UI pieces |
| Accepts props/data | Yes, via array | Yes, via attributes — cleaner syntax |
| Has its own PHP class | No | Optional (yes, if generated with `--resource` logic) |

## Blade Components

**Component**: a self-contained, reusable piece of UI — Blade's answer to something like a React component.

```bash
php artisan make:component Alert
```

This generates **two** files:
- `app/View/Components/Alert.php` — the component's PHP logic/class (optional to modify for simple components).
- `resources/views/components/alert.blade.php` — the actual Blade markup.

**The component's Blade file:**

```blade
{{-- resources/views/components/alert.blade.php --}}
<div class="alert alert-{{ $type }}">
    {{ $slot }}
</div>
```

**Using it anywhere in your app:**

```blade
<x-alert type="success">
    Product saved successfully!
</x-alert>
```

- **`<x-alert ...>`**: the `x-` prefix tells Blade "this is a component," followed by the component's file name (`alert` → `alert.blade.php`).
- `type="success"` — passed in as a plain string attribute, available inside the component as `$type`.
- **Passing a PHP variable instead of a string** requires a colon prefix: `<x-alert :type="$status" />`.

## Slots

- **Slot**: the mechanism that lets you inject custom content *into* a component from wherever it's used — like `{{ $slot }}` in the Alert example above, which captured everything between `<x-alert>` and `</x-alert>`.

**Named slots** — for components needing more than one content area:

```blade
{{-- resources/views/components/card.blade.php --}}
<div class="card">
    <div class="card-header">{{ $header }}</div>
    <div class="card-body">{{ $slot }}</div>
</div>
```

```blade
<x-card>
    <x-slot:header>
        Product Details
    </x-slot:header>

    This is the main card content.
</x-card>
```

- Anything **not** wrapped in a named `<x-slot:name>` tag falls into the default `$slot`.

## Conditional Classes with `@class`

```blade
<div @class([
    'badge',
    'badge-success' => $product->in_stock,
    'badge-danger' => !$product->in_stock,
])>
    {{ $product->in_stock ? 'In Stock' : 'Sold Out' }}
</div>
```

- **`@class([...])`**: always includes plain string entries (`'badge'`), and conditionally includes keyed entries only when their value evaluates to `true` — cleaner than manually concatenating class strings with PHP ternaries.

## Authentication Directives

```blade
@auth
    <p>Welcome back, {{ auth()->user()->name }}!</p>
@endauth

@guest
    <a href="{{ route('login') }}">Log in</a>
@endguest
```

- **`@auth`**: renders its content only if a user is currently logged in.
- **`@guest`**: the inverse — renders only if no user is logged in.
- Full authentication setup (how a "logged in user" gets there in the first place) is covered in note 09.

## Stacks (Pushing Scripts/Styles)

Sometimes a specific child page needs to add its *own* extra `<script>` or `<style>` tag to the shared layout, without editing the layout file itself.

**In the layout:**

```blade
<head>
    @stack('styles')
</head>
<body>
    ...
    @stack('scripts')
</body>
```

**In a specific child page:**

```blade
@push('scripts')
    <script src="/js/product-gallery.js"></script>
@endpush
```

- **`@stack('name')`**: a placeholder in the layout, similar to `@yield`, but can receive contributions from *multiple* different child views.
- **`@push('name') ... @endpush`**: adds content to that named stack from a child view.

## Raw PHP Inside Blade

```blade
@php
    $discountedPrice = $product->price * 0.9;
@endphp

<p>{{ $discountedPrice }}</p>
```

- **`@php ... @endphp`**: lets you drop into plain PHP for small calculations directly inside a Blade file.

> ⚠️ **Warning:** Using `@php` for actual business logic (calculating discounts, formatting complex data) is a common beginner mistake. That logic belongs in your Controller or Model — Blade files should stay focused on *display*, not computation. Overusing `@php` is a sign your architecture needs cleanup, which matters a lot as you move toward senior-level code (note 15).

## Custom Directives

For advanced/senior-level use: you can define your **own** Blade directives when you find yourself repeating the same formatting logic everywhere.

```php
// In a Service Provider's boot() method
use Illuminate\Support\Facades\Blade;

Blade::directive('shortdate', function ($expression) {
    return "<?php echo ($expression)->format('M d, Y'); ?>";
});
```

```blade
<p>@shortdate($product->created_at)</p>
```

> 💡 **Tip:** You won't need custom directives often as a beginner — Laravel's built-in directives cover nearly everything. Keep this in your back pocket for later once you're comfortable.

## Quick Revision

- Blade files live in `resources/views/` and end in `.blade.php`; they compile to plain cached PHP, so there's no real performance trade-off for using them.
- `{{ }}` auto-escapes output (safe by default); `{!! !!}` does not — only use it on fully trusted HTML.
- `@if/@elseif/@else/@endif`, `@unless`, `@isset`, and `@empty` handle conditionals; `@foreach`, `@forelse` (with a built-in empty case), `@for`, and `@while` handle loops.
- Inside any `@foreach`, the `$loop` variable gives you `$loop->first`, `$loop->last`, `$loop->iteration`, etc. for free.
- `@extends` + `@section` + `@yield` build a shared layout system — the direct equivalent of a `<Layout>` component with a `{children}` slot in React.
- `@include` pulls in simple reusable partials; **Components** (`php artisan make:component`, used as `<x-name>`) are the more powerful, reusable option — Blade's version of React components, complete with **slots** for injecting content.
- `@stack` / `@push` let a specific child page contribute extra scripts/styles to the shared layout without editing it directly.
- Keep real business logic (calculations, data transforms) out of Blade files — that belongs in Controllers/Models. `@php` blocks should stay minimal.
